= Vert.x S3 Client

An asynchronous client for Amazon S3 and S3-compatible storage (DigitalOcean Spaces,
MinIO-compatible servers), based on Vert.x.

WARNING: The module is being rewritten. The API is incomplete and will change between versions.

NOTE: `S3Client`, `S3Presigner` and `S3Exception` have the same simple names as AWS SDK v2 types.
In a file that uses both libraries, refer to one of them by its fully qualified name.

== Using the client

Add the dependency to your build. It needs Vert.x 5.2 and Java 11 or later.

* Maven (in your `pom.xml`):

[source,xml]
----
<dependency>
  <groupId>${maven.groupId}</groupId>
  <artifactId>${maven.artifactId}</artifactId>
  <version>${maven.version}</version>
</dependency>
----

* Gradle (in your `build.gradle` file):

[source,groovy]
----
implementation '${maven.groupId}:${maven.artifactId}:${maven.version}'
----

A client is configured with `S3ClientOptions`. The endpoint URI is the single source of scheme,
host and port, and the region is required. Here is DigitalOcean Spaces:

[source,$lang]
----
{@link examples.Examples#createForSpaces}
----

and a local MinIO-compatible server:

[source,$lang]
----
{@link examples.Examples#createForLocalMinio}
----

`S3Client.create` validates the options and throws `IllegalArgumentException` if they are invalid
(missing endpoint, region or credentials, ...).

Payload signing isn't configurable. Over HTTPS, request bodies are sent as `UNSIGNED-PAYLOAD`:
TLS protects them, and the signature still covers the method, path, query and headers. Over plain
HTTP, every body is signed with its SHA-256.

=== Addressing style

Buckets are addressed path-style by default (`https://host/bucket/key`), which every
S3-compatible server supports. *This differs from the AWS SDK default*, which is
virtual-hosted-style (`https://bucket.host/key`). To use virtual-hosted-style:

[source,$lang]
----
{@link examples.Examples#virtualHostedStyle}
----

DigitalOcean Spaces documents virtual-hosted-style addressing, as in the Spaces example above. With
it over HTTPS, bucket names can't contain dots (see "Buckets").

=== Credentials

Credentials are static: an access key and a secret key, plus a session token for temporary
credentials, set with `setCredentials`. Like every other option, they can come from JSON
configuration:

[source,$lang]
----
{@link examples.Examples#createFromJsonConfig}
----

The client copies the credentials when it is created. To use other keys, create a new client and
close the old one.

Secrets are read from JSON, but never appear in `toJson()` or `toString()` of the options:
`toJson()` is for logging and inspection, not for copying options with their credentials.

== Contexts and threading

Every asynchronous method captures the caller's Vert.x context and completes its `Future` on
that context, whether the caller is an event-loop, worker or virtual-thread verticle. A client is
thread-safe and can be shared between verticles.

A client created inside a verticle is closed automatically when that verticle is undeployed,
like a Vert.x `HttpClient`. Otherwise it is closed together with its `Vertx` instance.

== Objects

Object keys are 1 to 1024 bytes of UTF-8 and may contain any character: the client encodes them on
the wire. An invalid key fails with an `S3ClientException` before any request is sent.

----
{@link examples.Examples#putObject}
----

with a content type and user metadata (sent as `x-amz-meta-*` headers; names are case-insensitive,
values are printable US-ASCII):

[source,$lang]
----
{@link examples.Examples#putObjectWithOptions}
----

Metadata values that aren't US-ASCII are rejected, not encoded. If you need them (e.g. Arabic file
names), URL-encode them yourself, or keep such data in the object key (keys accept any Unicode
character) or in your own database.

=== Uploading files

`putFile` uploads a file of any size up to S3's 5 TiB limit, without buffering it and without
blocking the event loop:

[source,$lang]
----
{@link examples.Examples#putFile}
----

The file's size is read and the file opened before any request, so a missing file or a directory
fails with an `S3ClientException` without contacting the server. A file of up to 8 MiB is one
PutObject. A larger file is a multipart upload with two parts in flight, each streamed straight
from its byte range of the file; the part size grows with the file (8 MiB up to 78 GiB, then the
smallest multiple of 8 MiB that fits 10,000 parts). Memory use stays at a few chunks per upload,
whatever the file size.

Don't change the file during the upload. A file that shrinks fails the upload, but a file changed
in place without changing its length is uploaded as found, partly old and partly new.

=== Uploading streams

`putObject` also takes a `ReadStream<Buffer>` of unknown length, such as an HTTP request body:

[source,$lang]
----
{@link examples.Examples#putObjectFromRequest}
----

The stream is read with backpressure, on the context that called `putObject`. A stream that ends
within 8 MiB is one PutObject; a longer one is a multipart upload of 8 MiB parts, one uploading
while the next fills. A stream is limited to 10,000 parts (78 GiB); use `putFile` for larger files.
If the arguments are invalid, the stream isn't read and stays paused, so answer the request in
`onFailure`.

IMPORTANT: A streamed upload buffers up to two parts, about 16 MiB, while it runs. Size your memory
for the streamed uploads you run at once: 50 concurrent uploads need about 800 MiB. `putFile`
needs only a few chunks per upload; prefer it when the data is already in a file.

Both forms send the ETag of the object, or of the multipart upload (`"…-N"`), as the result. If
anything fails (the stream, the file, a part, the completion) or the client is closed during the
upload, the multipart upload is aborted, so no parts are left behind, and the future fails with the
original cause. Over plain HTTP each part is signed with its SHA-256: streamed parts are hashed as
they arrive, and file parts are read twice, once to hash them. Over HTTPS nothing is hashed
(`UNSIGNED-PAYLOAD`).

=== Downloading small objects

`getObject` buffers the whole object in memory, so it is for *small objects only*. An object larger
than `S3ClientOptions.maxBufferedObjectSize` (default 4 MiB) fails with an `S3ClientException`
pointing to `getObjectStream`, without its body being read.

[source,$lang]
----
{@link examples.Examples#getObject}
----

=== Streaming objects of any size

`getObjectStream` never buffers the object. Its future completes when the response headers arrive:
an error such as `NoSuchKey` fails it before any data is streamed. On success you get an
`S3ObjectStream`, a `ReadStream<Buffer>` with real backpressure that also carries the object's
metadata. It is handed out *paused*, and its handlers run on the context that called
`getObjectStream`.

To save it to a file, open the file first, so that a failure to open it doesn't leave a stream
behind that you would have to cancel:

[source,$lang]
----
{@link examples.Examples#getObjectStreamToFile}
----

To send it as an HTTP response, set the `Content-Length` from the metadata when the server reports
it, and use `send`. Cancel the stream when the HTTP client disconnects (the response's close
handler) and when `send` fails. `send` alone doesn't notice a disconnect: it fails only when a write
fails, and then Vert.x resumes the stream without a handler, so the rest of the object is
downloaded for nothing. While no data arrives, it doesn't fail at all and the stream keeps its
connection:

[source,$lang]
----
{@link examples.Examples#getObjectStreamToHttpResponse}
----

The same applies to any pipe: when a write fails, Vert.x stops writing and resumes the source.
Cancel the stream when `pipeTo` fails.

A single byte range can be requested with an HTTP `Range` value (`bytes=0-99`, `bytes=100-` or
`bytes=-100`):

[source,$lang]
----
{@link examples.Examples#getObjectRange}
----

IMPORTANT: Until it ends, an object stream holds a pooled HTTP connection. Read it to the end or
cancel it. A stream that is neither consumed nor cancelled never releases its connection.

[source,$lang]
----
{@link examples.Examples#cancelObjectStream}
----

NOTE: With Mutiny, cancelling the subscription of a `Multi` made from the stream (with
`MultiHelper.toMulti`, or `toMulti()` on generated bindings) detaches its handlers and resumes the
stream instead of cancelling it, so the rest of the object is still downloaded. Call `cancel()` on
the stream yourself when you cancel the subscription, e.g. in `onCancellation()`.

=== Listing objects

`listObjects` returns one page of a bucket's objects, in key order, optionally limited to a prefix:

[source,$lang]
----
{@link examples.Examples#listObjects}
----

With a delimiter, keys below the next delimiter are grouped into common prefixes: the "folders"
of a key hierarchy.

[source,$lang]
----
{@link examples.Examples#listFolders}
----

A page holds at most `maxKeys` entries (1000 by default). There is no paging helper: while a page
is truncated, ask for the next one with its continuation token.

[source,$lang]
----
{@link examples.Examples#listAllKeys}
----

Continuation tokens haven't always been reliable on S3-compatible servers (the DigitalOcean Spaces
documentation lists a ListObjectsV2 pagination issue). If a listing without a delimiter repeats keys
or stops early, ask for the next page with `setStartAfter` set to the last key of the previous page
instead of the continuation token.

Keys of any characters (spaces, `+`, `%`, Arabic, ...) are returned decoded.

== Presigned URLs

A presigned URL lets whoever holds it download (`GET`) or upload (`PUT`) one object until it
expires, without credentials. A browser or a mobile app transfers the bytes directly with the
storage, and your backend never handles them.

Presigning is pure computation with no I/O, so it is synchronous and returns the URL as a `String`.
Get a presigner from a client, or create one without a `Vertx` instance:

[source,$lang]
----
{@link examples.Examples#createPresigner}
----

A presigner uses the endpoint, region, addressing style and credentials of its options, and ignores
the transport settings. It holds no resources, is thread-safe, and keeps working after the client is
closed.

The expiry is an amount and a `TimeUnit`, or a `Duration` in Java: positive, a whole number of
seconds, and at most 7 days. Invalid arguments throw `IllegalArgumentException`; bucket names and
keys follow the same rules as for the client.

=== Public endpoint

On Kubernetes, your backend often reaches the storage at an in-cluster address that apps outside the
cluster can't reach. Set `publicEndpoint` to the endpoint that URLs should point to. It defaults to
`endpoint`, and only presigning uses it:

[source,$lang]
----
{@link examples.Examples#presignerWithPublicEndpoint}
----

The URL's host, with its port when it isn't the default, is part of the signature. A proxy or
ingress in front of the storage must pass the `Host` header through unchanged.

Point upload URLs at the storage endpoint, not at a CDN: on DigitalOcean Spaces, the CDN endpoint
accepts request bodies of at most 8100 KiB, so larger presigned uploads and multipart parts must go
to the origin endpoint (`<region>.digitaloceanspaces.com`).

=== Uploads from browsers and mobile apps

The backend stays in charge of what gets stored:

. The app asks the backend for an upload, announcing the file's content type, its size and the
base64 MD5 of its bytes.
. The backend authorizes the user, checks what the app announced (an allowed type, a size within
its limit), chooses the key (never the app), and returns a presigned `PUT` request that signs the
content type, the MD5 and the size.
. The app sends exactly those bytes, with exactly the returned headers, to the URL.
. The app tells the backend that the upload is done, and the backend checks the object with
`headObject` before trusting it.

[source,$lang]
----
{@link examples.Examples#presignUpload}
----

`S3PresignPutOptions` turns `Content-Type`, `Content-MD5` and `Content-Length` into signed headers,
and the methods taking options return an `S3PresignedRequest`: the URL, the method and the headers
to send. Its `toJson()` can be returned to the app as is; its `toString()` never shows the URL. The
server rejects an upload that sends another value for a signed header, or leaves one out, one
whose body doesn't match its `Content-MD5`, and one of any other size than its signed
`Content-Length`. A signed length is 0 to 5 GiB, S3's limit for a single `PUT`; larger files are
multipart uploads. Without options, `presignPut` returns just the URL, and only
`Host` is signed.

[source,$lang]
----
{@link examples.Examples#verifyUpload}
----

The key to verify is the one the backend issued, not one sent by the app. `headObject` returns what
S3 recorded; it doesn't inspect the bytes.

=== Rules for presigned URLs

* *Keep the expiry short*: minutes, just enough for the transfer to start.
* *A URL is a bearer token.* Anyone who has it can use it until it expires, and it can't be revoked.
Never log presigned URLs, and hand them out only over HTTPS.
* *Signing `Content-Length` pins the exact size the backend approved.* Check the size the app
announces against your limit before presigning: the server then rejects a body of any other size.
Still verify the object with `headObject` after the upload, and delete it if it isn't acceptable.
A signed `Content-MD5` pins the exact bytes as well. Without a signed length, a presigned `PUT`
accepts any size up to S3's 5 GiB.
* *Send a real `Content-Length` header, never chunked transfer encoding*, when the length is
signed: a chunked body has no `Content-Length`, so the server rejects it (Silo answers 411
`MissingContentLength`, Ceph RGW 403 `SignatureDoesNotMatch`). HTTP clients set the header for a
body of known size; a streamed upload must set it explicitly (e.g. OkHttp's
`RequestBody.contentLength()`, Dart's `StreamedRequest.contentLength`). Browsers compute it from
the body: `Content-Length` is a forbidden header name in `fetch` and `XMLHttpRequest`, so browser
code sends the other returned headers and leaves it out. It needs no CORS entry.
* *Use unique keys chosen by the backend*, e.g. with a UUID. A presigned `PUT` replaces any object
with the same key; there is no overwrite protection.
* *Send signed headers byte for byte, and the body as bytes.* Some HTTP clients change headers: Dart's
`http` package, for example, adds `; charset=utf-8` to the `Content-Type` of a string body, which
the server then rejects. Without options only `Host` is signed, so the uploader may send any
`Content-Type`, which S3 stores and serves back: treat it as untrusted input.
* *Private documents*: sign `Cache-Control: no-store`, and point URLs at the storage endpoint, not
at a CDN-proxied domain, which may cache the response and serve it to others.
* *Browser uploads* (e.g. Flutter web) are cross-origin requests: the bucket needs a CORS rule that
allows your app's origin, the `PUT` method and the headers it sends, including `Content-Type` and
`Content-MD5` when they are signed. Configure it with your storage provider's tools; this library
doesn't manage it. Native mobile apps don't need one.

== Multipart uploads

Large files, such as videos of hundreds of MB to GB, are uploaded in parts: a browser or mobile
app uploads them directly through presigned part URLs, several at a time, and can resume after a
lost connection without starting over. The backend stays in charge:

. The app announces the file's size and type. The backend authorizes the user, chooses the key and
the part size, and creates the upload. It stores the upload id with the user and the key.
. The backend presigns part URLs, a batch at a time.
. The app uploads the parts, with the returned headers, and reports each part's number and `ETag`
(a response header of the part upload).
. The backend completes the upload, then checks the object before trusting it.

[source,$lang]
----
{@link examples.Examples#startMultipartUpload}
----

`createMultipartUpload` takes the options of `putObject`: the content type and user metadata are
set here for the whole object, since parts have none. S3's rules for the parts: 1 to 10,000 parts,
numbered 1 to 10,000; each 5 MiB to 5 GiB, except the last, which may be smaller.

[source,$lang]
----
{@link examples.Examples#presignParts}
----

Presign part URLs on demand, a batch at a time, with a short expiry: the app asks for more as it
goes, and for fresh ones when it resumes. `presignUploadPart` with `S3PresignUploadPartOptions`
signs each part's `Content-Length`, as the example does (the part size, or the remainder for the
last part), and can also sign a `Content-MD5` per part, as for a presigned `PUT`. A part is at most
5 GiB. The presigner can't check the 5 MiB minimum for every part but the last, because it doesn't
know which part is last: the server enforces it on completion (`EntityTooSmall`).

[source,$lang]
----
{@link examples.Examples#completeMultipartUpload}
----

The parts may be reported in any order, e.g. as parallel uploads finish: `completeMultipartUpload`
sends them in part-number order, as S3 requires, and part numbers may have gaps. The server rejects
a wrong `ETag` (`InvalidPart`) and a part other than the last one under 5 MiB (`EntityTooSmall`);
the upload then stays open. With signed part lengths, the parts add up to the size the backend
approved; still check the object with `headObject` after completing.

=== Resuming

To resume, the app comes back with the upload id the backend stored. If it lost the `ETag`s of the
parts already uploaded, `listParts` returns them, with their sizes; the app then uploads only the
missing parts, with fresh URLs. If `listParts` fails with `404`, the upload is gone (aborted,
completed or cleaned up): AWS answers `NoSuchUpload` and Ceph RGW-based servers `NoSuchKey`. Start a
new upload.

[source,$lang]
----
{@link examples.Examples#missingParts}
----

=== Giving up and cleaning up

Until an upload is completed or aborted, its parts are stored, and usually billed. Abort an upload
the app gives up on with `abortMultipartUpload`. A part that was still being uploaded may be stored
after the abort; aborting again removes it.

Uploads can also be abandoned without anyone noticing: an app that never comes back, or a backend
that created an upload but crashed before storing its id. A cleanup job finds them with
`listMultipartUploads` and aborts the old ones:

[source,$lang]
----
{@link examples.Examples#abortStaleUploads}
----

For an upload that is already gone, AWS answers `404 NoSuchUpload` while some S3-compatible servers
answer success: treat both as done. (Asked to list the parts of an aborted upload, Ceph RGW-based
servers answer `404 NoSuchKey`, which means the same.) On AWS, a prefix limits the listing to keys that start with it;
some servers (MinIO-compatible ones, for example) only match whole keys, so a cleanup job should
list the whole bucket and filter. As an extra safety net, a bucket lifecycle rule
(`AbortIncompleteMultipartUpload`) can abort old uploads on servers that support it; configure it
with your storage provider's tools, as this library doesn't manage lifecycle rules. DigitalOcean
Spaces deletes incomplete multipart uploads automatically after 30 days, according to its
documentation; a cleanup job removes them sooner, and works on every server.

=== Part sizes and rules

* *Part size*: 8 to 16 MiB suits large media from mobile apps: a failed part is cheap to retry, and
a 2 GiB video in 16 MiB parts takes 128 requests. Files above 78 GiB (10,000 parts of 8 MiB) need
larger parts; the `startMultipartUpload` example computes the size.
* *Parallelism*: 3 or 4 parts at a time is usually enough to fill a mobile connection.
* *DigitalOcean Spaces*: upload parts to the origin endpoint, not the CDN endpoint, which accepts
request bodies of at most 8100 KiB, less than the part sizes above.
* *Browsers* need a CORS rule on the bucket that allows `PUT` and *exposes the `ETag` header*;
without it the app can't read the part `ETag`s.
* *Completion*: S3 can report a failure after it has started a `200` response; such a response
fails with an `S3ServiceException` whose status code is `200`. Completing can take a while for
large objects.

== Errors

Failures are `S3Exception` instances. An `S3ServiceException` means the server answered with an
error response: it carries the HTTP status, the S3 error code (when the response has an error
document), and the request id to quote in support requests. Any other failure (connection, TLS,
an unreadable response, an invalid argument, a closed client) is an `S3ClientException`.

[source,$lang]
----
{@link examples.Examples#handleErrors}
----

A server that is overloaded, or that limits a client's request rate, answers `503 SlowDown`
(DigitalOcean Spaces documents such limits). The library doesn't retry: retry these failures in the
application, with exponential backoff and jitter, and only for requests that are safe to repeat.
